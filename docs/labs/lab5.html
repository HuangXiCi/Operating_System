1.1 xv6 的物理页分配方式

在 xv6 中，物理内存被划分为 4 KiB 的页。内核映像结束位置 end 之后，从 PGROUNDUP(end) 开始的完整页可供分配；PHYSTOP 是内存上界，不是可分配页的起始地址。原始 kalloc() 和 kfree() 只管理单页，使用一条单向链表维护空闲页，无法保证连续物理页的分配。

任务 1：读懂原始物理页分配器

阅读原始 kernel/kalloc.c，画出 kinit() → freerange() → kfree() 建立空闲链表的过程， 再说明 kalloc() 如何取出一页、kfree() 如何归还一页。 在实验报告中画出至少三页的链表变化，并分析单页头插分配的优点与局限。

提示：先分清地址和页号

end 是地址，不一定在页边界；PGROUNDUP(end) 才是第一张 可能被分配的完整页的起点。原始 kalloc() 只取链表头，不会遍历 链表搜索“最合适”的页。

1.2 伙伴系统

完成本部分后，应能够解释以下问题：

  • 为什么“两个空闲块相邻”仍不足以保证它们可以合并？

  • 申请连续的 2^n 页时，怎样找到并拆分更大的块？

  • 释放一个块时，怎样计算它的伙伴，并逐级合并？

  • xv6 原有的 kalloc() 和 kfree() 怎样兼容新的分配器？

从单页分配到块分配

假设物理内存被划为等大的页，并从 0 开始编号。伙伴系统把页组织为 大小为 2 的幂、起点按块大小对齐 的连续块。块的“阶”表示它包含多少页：

例如，第 2 阶块可以是页 [8..11]，它的起点 8 是 4 的倍数。 页 [12..15] 是它的伙伴：两块大小相同，并且恰好组成以 8 为起点的 第 3 阶块 [8..15]。伙伴并非任意相邻块：第 2 阶的 [4..7] 与 [8..11] 虽然相邻，却不能合并成正确对齐的 第 3 阶块。

对首页页号 i、阶数 n，伙伴首页页号为：

buddy(i, n) = i XOR (1 << n)

XOR 是按位异或。它翻转区分同一大块左右两半的那一位： 8 XOR 4 = 12，12 XOR 4 = 8。使用此公式的前提是页号 从同一段对齐的物理内存起点计算，且每个块按自身大小对齐。

需要保存哪些状态

理论上需要为每一阶维护一条空闲块链表 freelist[n]，还要知道一个块是否 空闲、属于哪一阶。实现时可只在**块的首页**记录阶数和空闲状态；块内其他页 不是独立块头。维护如下不变量：

  1. 一个空闲块只出现在与其阶数相同的链表中；

  2. 两个空闲的同阶伙伴应合并为一个高一阶块；

  3. 已分配块不会出现在任何空闲链表中；

  4. 每个块的首页、大小和对齐方式一致。

第二条说明合并应持续进行，而不是只检查一次。只有保持这些不变量， 分配器才能通过查找某阶链表判断是否有足够大的连续区域。

提示：阶数不是块的数量

第 0～15 阶共有 16 种大小，但同一阶可以同时存在许多块。 例如四个互不相邻的空闲页都是第 0 阶块，分别拥有自己的块首页； 不能只用一条“第 0 阶状态”表示它们。

申请：向上查找，向下拆分

申请第 n 阶块时，先查看 freelist[n]。如果为空，就向更高阶 查找；若找到第 m 阶块，其中 m > n，便反复平分：

从第 3 阶的 [8..15] 申请第 1 阶块

[8..15]  第 3 阶
  ├─ [8..11]   第 2 阶，继续拆
  │    ├─ [8..9]    第 1 阶，返回
  │    └─ [10..11]  第 1 阶，放回空闲链表
  └─ [12..15] 第 2 阶，放回空闲链表

若所有不小于 n 阶的链表都为空，申请失败。这里返回的两页在 物理地址 上连续；它们是否被映射到用户虚拟地址，是页表管理的另一件事。

释放：检查伙伴，向上合并

释放第 n 阶块时，先验证地址、对齐、阶数及“已分配”状态，再计算 同阶伙伴。只有伙伴 空闲且同阶，才能从空闲链表摘除它，把两块合为 第 n+1 阶。新块取两者中较低的首页页号，然后继续检查更高阶伙伴。 无法再合并时，将最终块插入其所属阶数的链表。

例如先释放 [8..11]、再释放 [12..15]：

[8..11]  +  [12..15]  →  [8..15]
第 2 阶     第 2 阶       第 3 阶

若 [12..15] 正在使用，[8..11] 必须作为第 2 阶块保留； “地址相邻”不能替代对伙伴状态的检查。

任务 2：手工推演拆分与合并

以页号 8～15 为例，画出从一个第 3 阶空闲块申请第 1 阶块后， 各阶空闲链表中剩余的块；再推演释放时怎样逐级合并。 分别计算页号 8 和 12 作为第 2 阶块首页时的伙伴。 最后回答：连续的 2 MiB 物理内存需要多少页、应申请第几阶？

代价与适用场景

每次查找、拆分和合并最多跨越最高阶数那么多级。若空闲链表支持根据节点 直接摘除伙伴，结构操作的复杂度为 O(log N)，其中 N 是页数。 实现还可能为调试而填充整块内存；这部分耗时与块大小成正比。

伙伴系统适合按 2 的幂申请连续物理页，也能在释放后恢复大块。它的代价是 内部碎片：申请 5 页需要占用第 3 阶的 8 页块，暂时浪费 3 页。 单一全局锁还可能在多核频繁分配时形成争用。

1.3 改造准备与元数据

先看原始代码和内存范围

原始 kernel/kalloc.c 只有一条单向空闲页链表。kinit() 把 end 到 PHYSTOP 之间的完整页逐一交给 kfree()； kalloc() 从链表头取一页。它不会搜索连续页，也没有合并机制。

改造前先读以下文件：

KERNBASE 和 PHYSTOP 确定管理的物理地址范围。

PGSIZE 为 4096，PGROUNDUP 用于页对齐。

本实验的 PHYSTOP - KERNBASE 为 128 MiB，即 2^15 页， 因此实现定义 MAX_ORDER = 15。内核已经占用部分内存，实际空闲范围 未必包含一个完整的第 15 阶块。

替换空闲链表并建立元数据

在 kernel/kalloc.c 中，把单个 freelist 改为 freelist[MAX_ORDER + 1]。空闲块首页用 struct run 存储 next 和 prev，这样已知伙伴地址时可以直接从链表摘除伙伴。 再增加两个以物理页号为索引的数组：

#define NPAGES ((PHYSTOP - KERNBASE) / PGSIZE)
#define MAX_ORDER 15

struct run {
  struct run *next;
  struct run *prev;
};

struct {
  struct spinlock lock;
  struct run *freelist[MAX_ORDER + 1];
  signed char order[NPAGES];
  uchar free[NPAGES];
} kmem;

order[i] 只记录块首页的阶数；块内部页和保留页记为 -1。 free[i] 区分空闲块头和已分配块头。pageindex(pa) 将地址转为页号：

i = ((uint64)pa - KERNBASE) / PGSIZE;

元数据是内核的静态数组，位于 end 之前，不会被当作空闲页分配。 pushfree() 负责插入空闲链表，removefree() 负责摘除； 它们与元数据更新都由 kmem.lock 保护。 NPAGES 是从 KERNBASE 到 PHYSTOP 的总页数， 不是当前空闲页数。数组按页号直接索引，查询伙伴状态无需扫描链表。

  1. 在 kernel/kalloc.c 定义 NPAGES、 MAX_ORDER、各阶空闲链表与页状态数组。
  2. 实现 pageindex()，把物理地址换算为相对 KERNBASE 的页号。
  3. 实现 pushfree() 和 removefree()： 插入或摘除指定阶数的块，同时维护链表指针与 free[]。

完成后，请解释为什么合并时已经知道伙伴地址，却仍需要双向链表。

小心：链表指针写在空闲块内

struct run 占用的是空闲块首页开头的字节。块被分配后， 这些字节属于调用者，不能继续读取 next 或 prev。 若释放时要用 memset 填充页面，应先核对元数据，再填充， 最后用 pushfree() 写入新的链表指针。

1.4 改造初始化

kinit() 先把全部 order[] 设为 -1，然后从 PGROUNDUP(end) 起逐页初始化，到 PHYSTOP 为止。 每个新加入的页先视为第 0 阶块，再交给 kfree_pages(p, 0)。 这会立即尝试与已经加入的空闲伙伴合并。PHYSTOP 本身是上界， 不代表一页可分配内存。

从第一张空闲页推演

为了看清每一步，假设 第一个可分配页的页号是 8。页号 8 按两页、 四页和八页块的大小对齐，因此随后加入的页 9、10、11 能演示逐级合并。 这里的页号由 pageindex(pa) 计算，是相对 KERNBASE 的页号； 它不是从物理地址 0 开始计算的页号。

第一次循环：加入页 8。 kinit() 先设置 order[8] = 0， 表示页 8 暂时是一个第 0 阶块的首页。free[8] 初始为 0。 kfree_pages() 计算第 0 阶伙伴：8 XOR 1 = 9。页 9 尚未加入， 所以不能合并。pushfree() 将页 8 头插到 freelist[0]， 并设置 order[8] = 0、free[8] = 1。

第二次循环：加入页 9。 kinit() 暂时设置 order[9] = 0， 而 free[9] 仍为 0。kfree_pages() 算出 9 XOR 1 = 8；页 8 是空闲的第 0 阶伙伴，因此执行以下动作：

  1. removefree(8, 0) 把页 8 从 freelist[0] 摘除，并将 free[8] 改为 0；

  2. 两页合成第 1 阶块。页 9 不再是块首页，故 order[9] = -1；

  3. 新块首页取较低页号 8，局部变量 order 从 0 增至 1， 并将 order[8] 更新为 1；

  4. pushfree(8, 1) 把新块 [8..9] 头插到 freelist[1]，设置 free[8] = 1。

注意，代码增加的是 kfree_pages() 的局部变量 order， 然后将新阶数写回块首页；并非直接对 order[8] 做自增。 页 9 的 free[9] 始终为 0，因为它不是空闲块的首页。

第三、四次循环：加入页 10 和 11。 加入页 10 时，其第 0 阶伙伴 10 XOR 1 = 11 尚未加入，因此页 10 暂留在 freelist[0]。 加入页 11 后，先将 [10] 与 [11] 合成第 1 阶块 [10..11]。此时继续计算新块的第 1 阶伙伴： 10 XOR 2 = 8，于是 [10..11] 又与空闲的 [8..9] 合为第 2 阶块 [8..11]。

加入页 8 后：   freelist[0] → [8]          order[8]=0, free[8]=1
加入页 9 后：   freelist[1] → [8..9]       order[8]=1, free[8]=1
加入页 10 后：  freelist[0] → [10]
                freelist[1] → [8..9]
加入页 11 后：  freelist[2] → [8..11]      order[8]=2, free[8]=1

最后一行中，页 9、10、11 都是块内页，order[] 为 -1。 这也说明 freelist[n] 的每个节点代表一个 2^n 页的块， 并非链表节点之间逐页连接。

对齐是这段推演的前提。 如果第一个可分配页是页号 9， 那么页 9 的第 0 阶伙伴是页 8，而页 10 的伙伴是页 11。 页 9 与 10 虽然相邻，加入第二页时也不能合并。 真实的 PGROUNDUP(end) 不保证落在页号 8 这样的边界上， 所以初始化得到的会是若干个不同阶数的空闲块。

pageindex() 负责从地址得到页号，供元数据访问和伙伴计算使用。 pushfree() 把一个块插入相应阶数链表； removefree() 则摘除 指定的块，可能要修改链表头，也可能要连接 它的前后节点。合并时已经通过异或算出了伙伴地址，双向链表让中间节点也能 直接摘除，不必从链表头寻找前驱。

任务 4：让 kinit 建立伙伴系统

初始化锁和 order[]，从 PGROUNDUP(end) 起逐页加入空闲区域。每页在交给 kfree_pages(p, 0) 前， 先把该页登记为第 0 阶、尚未空闲的块头。 在实验报告中按页号 8～11 复现上面的四次循环， 写出每次循环后非空的 freelist[]。

小心：按同一个基准计算伙伴

伙伴异或运算使用的是相对 KERNBASE 的页号，而不是 (pa - end) / PGSIZE。end 不一定按大块对齐； 若以它作为页号零点，相邻块可能被错误地认作伙伴。

1.5 实现多页申请和释放

kalloc_pages(order) 按理论部分的“向上查找、向下拆分”实现： 从请求阶数开始向上查找；没有合适块时返回 0。找到块后， 用 removefree() 将其取出。只要当前阶数仍大于请求阶数，就将 当前阶数减一，保留左半块继续拆，把右半块用 pushfree() 放回对应链表。最后把左半块记录为已分配的目标阶块，再返回其首页地址。 每次拆分都要更新两个子块的元数据，不能只修改链表。

kfree_pages(pa, order) 先检查阶数、地址范围、块对齐和分配状态， 再用页号异或计算伙伴。如果伙伴越界、不空闲或阶数不同，就停止合并； 否则用 removefree() 摘除伙伴，清理不再作为块首页的元数据， 以较低页号为新块首页继续向高阶合并。最后通过 pushfree() 把合并后的块放回对应链表。错误阶数或重复释放会触发 panic。

源码沿用 xv6 的调试填充值：申请后用 5 填充，释放时用 1 填充。它们不是零初始化；例如 uvmalloc() 仍要自行清零用户页。

任务 5：实现拆分与合并

  2. 实现 kfree_pages(pa, order)：检查地址与分配状态， 根据伙伴页号逐级合并；只有空闲且同阶的伙伴才能被摘除。
  3. 保护对空闲链表和页状态的共同修改；检查所有提前返回路径是否正确释放锁。

用页号 8～15 的例子逐行对照代码，说明每次拆分或合并后 order[]、free[] 和 freelist[] 的变化。

小心：传入的阶数必须与实际分配阶数相同

1.6 保留单页接口

在 kernel/defs.h 声明 kalloc_pages()、 kfree_pages()，并使原有接口成为第 0 阶包装：

void *kalloc(void) { return kalloc_pages(0); }
void kfree(void *pa) { kfree_pages(pa, 0); }

因此 kernel/vm.c、kernel/proc.c 等单页调用者无需修改。 若新调用者需要 4 个连续物理页，应配对使用：

void *pa = kalloc_pages(2);
if(pa != 0){
  // 使用 [pa, pa + 4*PGSIZE)
  kfree_pages(pa, 2);
}

不能把此块拆成四次 kfree()；分配器记录它是一个第 2 阶块。

普通 fork() 在创建子进程时复制父进程的用户内存。子进程随后若执行 exec()，这些刚复制的数据可能很快就被丢弃。COW 将复制推迟到实际写入时： 父子进程先共享物理页，某一方写入时再按需建立独立副本，同时保持数据隔离。

2.4 实现写时复制

本节应连通共享映射、引用计数、用户态写缺页以及 copyout() 四条路径。 仅让父子进程映射到同一物理页，尚不能保证写入隔离和正确回收。

共享映射与 COW 标记

修改 uvmcopy()：为子进程建立页表，但不立即复制父进程的用户物理页。 对父进程中原本可写的页面，清除父子页表项中的 PTE_W， 并设置一个软件使用的 PTE_COW 标记。可使用尚未占用的 RSW 位，例如：

kernel/riscv.h
#define PTE_COW (1L << 8)

原本只读的代码页仍可共享，但不能因为 fork() 被标记为可恢复写权限的 COW 页。 已经带有 COW 标记的页面再次 fork() 时，应保留其标记和只读状态。 保持懒分配留下的未映射区域，不得为了 fork() 预先补齐所有页面。

建立子进程映射成功后，确保共享页的引用计数增加。 若中途失败，应撤销已建立的子进程映射并正确恢复引用数量； 不能将仍被父进程使用的物理页提前释放。

用户态写缺页

用户程序写入不可写页面时产生 store page fault，scause == 15。 stval 给出出错虚拟地址；先检查地址范围，再向下对齐到页边界， 查找并验证该页表项。

只有有效、允许用户访问且带有 COW 标记的页面，才能按 COW 处理。 可新增 cowfault() 等辅助函数，实现以下行为：

  1. 分配新的物理页，将旧页内容复制到新页；

  2. 将当前进程的页表项改为映射新页，设置 PTE_W 并清除 PTE_COW；

  3. 更新地址转换缓存，减少旧物理页的引用；

  4. 返回用户态，重新执行引发缺页的写指令。

当旧页仅剩当前一个引用时，可以直接恢复写权限并清除 COW 标记， 省去分配和复制。该优化不应使真正的只读页变为可写。

当前源码已经由 usertrap() 将缺页交给 vmfault()， 可在 vmfault() 中区分“尚未映射的懒分配页面”和“已经映射的 COW 页面”， 保留现有懒分配处理。读缺页 scause == 13 不能被当成 COW 写入来处理。

地址非法、写入真正的只读页或分配新页失败时，应终止出错进程， 不能让整个内核崩溃。处理成功后，不要将保存的 epc 加 4： 本次必须重试原写指令，与前面实验处理 ecall 的返回位置不同。

内核向用户空间写入

read() 等系统调用可能通过 copyout() 将内核数据写入用户缓冲区。 copyout() 根据用户页表取得物理地址后复制数据， 这一路径不会自动通过用户态 store page fault 处理 COW。

因此，应在 copyout() 的逐页写入循环中检查目标映射： 目标是 COW 页时，先解除共享，成功后使用 更新后的物理地址 写入； 目标是真正的只读页时仍然拒绝写入。跨页写入时，每一页都要正确处理， 并保留原有的懒分配逻辑及失败返回约定。

权限更新与地址转换缓存

fork() 清除父进程的写权限，以及 COW 处理改变物理页或恢复写权限后， 应在适当位置调用 sfence_vma()，使修改后的页表生效。 否则 CPU 可能继续使用旧的地址转换或权限缓存。

必做：完成 COW 的完整路径

  1. 修改 uvmcopy()，实现共享映射，并区分原本可写页与真正只读页。

  2. 接入物理页引用计数，最后一个引用消失后才实际回收。

  3. 正确处理 COW 写缺页，并保持懒分配和原有异常处理功能。

  4. 修改 copyout()，覆盖内核写入及跨页情况。

  5. 处理分配失败、映射失败和进程退出，保证引用数量一致。

  6. 在页表权限或映射改变后，正确更新地址转换缓存。

vmtest
cowtest
usertests -q

vmtest 应显示地址转换正确、父子数据隔离；cowtest 应包含：

large-memory: OK
multi-generation: OK
copyout-cross-page: OK
reclaim: OK
ALL COW TESTS PASSED

usertests -q 最后应显示：

ALL TESTS PASSED

退出 QEMU：先按 Ctrl+A，松开后再按 X。回到 Linux 终端后执行：

make qemu CPUS=3

在新启动的 xv6 中，再运行同样三个测试，检查多核并发下的引用管理是否正确。 最终提交应包含单核和多核结果。结束时关闭不必要的调试打印， 并确认第一部分原有的测试仍然通过。

必做：完成验收并记录证据

  1. 保存普通 fork() 与 COW fork() 的 vmtest 对照结果。

  2. 在 CPUS=1、CPUS=3 下分别通过 cowtest 和 usertests -q， 同时确认 vmtest 正常。

  3. 说明大内存测试为什么能体现 COW 的作用，不能通过跳过测试、 修改成功输出或缩小压力区域来替代实现。

  4. 确认第一部分的分配器接口与测试仍然可用，提交整合后的工程。

若出现 exec cowtest failed，先检查 user/cowtest.c 是否存在、 UPROGS 是否包含该程序，以及是否已重新编译启动。 ls user/cowtest.c、rg 和 make 应在 Linux 终端执行， 不要在 xv6 shell 中执行这些源码检查命令。
